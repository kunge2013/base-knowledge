## Manage published functions管理已发布的函数

Once published, all types of functions can be viewed and managed using the **Ontology Manager**.  
一旦发布后，所有类型的函数都可以通过 Ontology Manager 进行查看和管理。

## Searching for functions 寻找功能

To search for functions, navigate to the **Ontology Manager** and select the **Functions** tab. You can search for functions by most metadata on the function, including but not limited to the function name, description, API name and RID.  
要查找函数，请进入 ontology 管理器，然后选择“Functions”选项卡。您可以根据函数的各种元数据来搜索函数，包括但不限于函数名称、描述、API 名称以及 RID 等参数。

![Search for functions in Ontology Manager](https://www.palantir.com/docs/resources/foundry/functions/functions-search.png)

## Function overview page 功能概述页面

After selecting a function in the Ontology Manager, you can view basic information about the function, including its inputs and outputs and any associated usage history for the function.  
在 Ontology Manager 中选择一个函数后，你可以查看该函数的基本信息，包括其输入和输出参数，以及与该函数相关的所有使用历史记录。

![View function overview in Ontology Manager](https://www.palantir.com/docs/resources/foundry/functions/function-overview.png)

## Function configuration page功能配置页面

Some types of functions allow you to configure resources such as timeouts or memory limits. If your function supports any configuration options, you can view and edit them in the **Configuration** tab. If this tab is not present, the function does not support any configuration options.  
某些类型的函数允许你配置资源相关的设置，比如超时时间或内存限制等。如果你的函数支持这些配置选项，你可以在“配置”选项卡中查看和编辑这些设置。如果不存在这个选项卡，那就说明该函数不支持任何配置选项。

Configuration overrides are applied on a per-function version basis. Depending on the application from which you publish your function, new versions may have the default configuration and you may need to reapply any configuration overrides.  
配置覆盖是基于每个功能的版本来应用的。根据您发布功能的应用程序不同，新版本可能会采用默认配置，这时您可能需要重新应用那些配置覆盖。

For example, you can configure the timeout on a TypeScript function as seen in the following image.  
例如，你可以像下面图片所示，配置 TypeScript 函数的超时时间。

![Manage function runtime configurations in Ontology Manager](https://www.palantir.com/docs/resources/foundry/functions/function-configuration.png)

### Configuration inheritance配置继承

Functions provide out-of-the-box support for inheriting configuration overrides when publishing new versions. The configuration is inherited from the prior stable version according to the semantic version specification. If publishing a non-stable version, configurations will be inherited from the prior version, regardless of whether it is a stable release.  
这些功能提供了即插即用的支持，使得在发布新版本时能够继承之前的配置设置。根据语义版本规范，配置会从上一个稳定版本中继承过来。如果发布的是非稳定版本，那么配置仍然会从上一个版本中继承过来，而不管那个版本是否是稳定版本。

Configuration inheritance requires your repository to contain updated template configurations. You can check the hidden `templateConfiguration.json` file to confirm the version your repository is on.  
配置继承要求你的仓库中包含已更新的模板配置。你可以检查隐藏的 `templateConfiguration.json` 文件，以确定你的仓库所使用的版本。

- For TypeScript v1 functions repositories, you must have `parentTemplateVersion >= 3.512.0`  
	对于 TypeScript v1 版本的函数仓库来说，你必须拥有 `parentTemplateVersion >= 3.512.0`
- For Python functions repositories, you must have `parentTemplateVersion >= 0.423.0`  
	对于 Python 函数的仓库来说，你必须使用 `parentTemplateVersion >= 0.423.0`

## Consistent snapshots 连续的快照记录

Function-backed actions automatically use one ontology snapshot for all read requests in a single run.  
这些基于函数的操作能够在一次运行中，为所有读取请求自动使用同一个本体快照。

Consistent snapshots provide the following qualities:  
一致的快照具有以下特性：

- **Data consistency:** Without snapshots, sequential ontology queries within a function could return different versions of data if the underlying data changed between requests. With snapshots, your function operates on a consistent view of the ontology, similar to snapshot isolation in a database transaction.  
	数据一致性：如果没有快照功能，那么在同一个函数内执行顺序查询时，如果底层数据在请求之间发生了变化，那么可能会得到不同版本的数据。而有了快照功能后，函数就可以基于一致的数据视图进行操作，这类似于数据库事务中的快照隔离机制。
- **Improved performance:** Reusing a single snapshot across all ontology requests significantly improves ontology read performance. A single function-backed action, along with any queries within, receives this benefit.  
	性能提升：在所有的本体查询中重复使用同一个快照文件，能够显著提高本体的读取性能。任何一个由函数支持的操作，以及其中的任何查询，都能从中受益。

### Snapshot configuration 快照配置

If you need to explicitly manage snapshots for advanced use cases, you can configure the snapshot behavior on the [function configuration page](#function-configuration-page) using the following options:  
如果您需要为高级使用场景显式管理快照，可以在函数配置页面通过以下选项来配置快照的相关设置：

- **Default (recommended):** Leave this option selected unless you encounter snapshot-related errors.  
	默认设置（推荐）：除非遇到与快照相关的错误，否则请保持此选项被选中状态。
- **Disable snapshots:** Use when you need the freshest data on each query during a run, or when you are hitting snapshot errors due to long-running workloads.  
	禁用快照功能：在需要每次查询都能获取最新数据的情况下使用，或者当由于运行时间过长的负载导致出现快照相关错误时，可以选择禁用快照功能。
- **Enable snapshots:** Use when you need a consistent point-in-time view across all reads and want better read performance, and your function can tolerate data not updating mid-run. This is not recommended for most use cases.  
	启用快照功能：在需要跨所有读取操作获取一个一致的时间点视图，并且希望提高读取性能时可以使用此功能。当然，如果你的函数能够容忍数据在运行过程中发生不更新的情况，那么就可以启用快照功能。不过，对于大多数使用场景来说，并不建议启用此功能。

By default, functions with sources run against live data without snapshots. Enforcing snapshots is not recommended since functions can perform writes or invoke external systems.  
默认情况下，那些有数据源的函数是在实时数据的基础上运行的，不会使用快照。不过，不建议强制使用快照，因为这些函数可能会执行写入操作或调用外部系统。

## Enforced limits 强制设定的限制

Several limits are in place to prevent functions from consuming too many resources when they are executed.  
已经实施了多项限制措施，以防止函数在执行过程中消耗过多的资源。

### Time limit 时间限制

Functions are limited to **60 seconds** of elapsed run time by default. These limits can be modified on the [function configuration page](#function-configuration-page).  
默认情况下，这些功能的运行时间限制为 60 秒。这些限制可以在功能配置页面上进行修改。

Functions are allowed to run for up to **280 seconds** when running in live preview, even if modified on the function configuration page.  
在实时预览模式下，即使是在功能配置页面上进行了修改，这些功能仍然可以运行长达 280 秒。

TypeScript v1 functions are additionally limited to **30 seconds** of CPU time, which is not configurable. When a function exceeds this threshold, the cause is often inefficient data loading logic. Refer to the section on [optimizing performance](https://www.palantir.com/docs/foundry/functions/optimize-performance/) for tips on how to avoid CPU timeouts.  
TypeScript v1 的函数运行时间也有限制，最多仅为 30 秒，这一点是不可配置的。当函数的运行时间超过这个限制时，通常是因为数据加载逻辑效率不高所导致的。有关如何避免 CPU 时间超出的建议，请参考性能优化相关的内容。

### Memory limit 内存限制

Memory limits differ between TypeScript v1, TypeScript v2, and Python functions.  
在 TypeScript v1、TypeScript v2 以及 Python 版本中，内存限制各不相同。

#### TypeScript v1

Function execution is limited to **128 Megabytes** of memory usage. This limit is rarely reached; often, functions run into time limits or object loading limits before memory limits.  
函数执行的内存使用量有限，仅为 128 兆字节。这个限制很少被突破；通常情况下，函数在达到时间限制或对象加载限制之前就会停止执行。

#### Deployed Python functions已部署的 Python 函数

Deployed Python functions have **2 Gigabytes** of memory usage by default. Currently, deployed Python functions cannot configure memory usage on the function configuration page.  
默认情况下，部署后的 Python 函数会占用 2 吉字节的内存资源。目前，在函数配置页面中无法对 Python 函数的内存使用情况进行设置。

#### Serverless Python and TypeScript v2 functions无服务器支持的 Python 和 TypeScript v2 函数

Serverless functions have **1024 Mebibytes** of memory usage by default. This can be configured from **512 Mebibytes** to **5120 Mebibytes** on the [function configuration page](#function-configuration-page).  
无服务器函数的默认内存使用量为 1024 兆字节。在函数配置页面中，可以将其配置为从 512 兆字节到 5120 兆字节不等。

### Multithreading 多线程处理

For TypeScript v1, function execution is on a single thread, allowing only one computation at any given time. However, you can parallelize loading of object sets or links. Refer to [optimizing performance](https://www.palantir.com/docs/foundry/functions/optimize-performance/) for more information.  
在 TypeScript v1 中，函数的执行是在单个线程上进行的，因此任何时候只能执行一项计算任务。不过，你可以并行加载对象集或链接。更多关于性能优化方面的信息，请参考相关文档。

For TypeScript v2 and Python functions, you can use multithreading with the built-in Node.js `worker_threads` and Python `threading` libraries.  
对于 TypeScript v2 和 Python 函数，可以使用内置的 Node.js 和 Python 库来实现多线程处理。

### Object set limits with TypeScript v1使用 TypeScript 1 版本可以设置对象的限制。

When using [object sets](https://www.palantir.com/docs/foundry/functions/api-object-sets/), calling `.all()` or `.allAsync()` will throw an error if:  
在使用对象集时，如果调用 `.all()` 或 `.allAsync()` ，将会引发错误。

- More than **100,000 objects** are loaded at once from the object set. In general, even loading tens of thousands of objects will run into time limits or memory limits. For use cases where you are running into this limit, consider fetching summary data using [aggregations](https://www.palantir.com/docs/foundry/functions/api-object-sets/#computing-aggregations) or fetching a subset of objects using [ordering and limiting](https://www.palantir.com/docs/foundry/functions/api-object-sets/#ordering-and-limiting).  
	从对象集中一次性加载了超过 10 万个对象。通常情况下，即使同时加载数万个对象，也会遇到时间限制或内存限制的问题。对于遇到这种限制的情况，可以考虑使用聚合函数来获取摘要数据，或者只加载部分对象。
- More than **3 [search arounds](https://www.palantir.com/docs/foundry/functions/api-object-sets/#search-around)** are used at once.  
	同时使用了超过 3 次搜索操作。

Some aggregation and bucketing operations have limits. See the [aggregations](https://www.palantir.com/docs/foundry/functions/api-object-sets/#computing-aggregations) section for details.  
一些聚合和分组操作存在局限性。详情请参阅相关章节。
