# OpenSpec 命令流程详解

> 本文档以通俗易懂的方式，讲解 OpenSpec 每个命令的完整处理流程。
> 通过"比喻 + 实例 + 流程图"帮助快速理解。

---

## 一、全局视角：OpenSpec 是什么？

### 1.1 一句话理解

OpenSpec 是一个**"先想清楚，再规划好，最后再动手"**的结构化开发工作流。

就像建房子：
1. **Explore（探索）** → 先看看这块地适合建什么，有什么限制
2. **Propose（提案）** → 画出设计图，列出需求清单，排好施工计划
3. **Apply（实施）** → 按施工计划一项一项干活
4. **Archive（归档）** → 验收合格后，把图纸存档

### 1.2 四个阶段一览

```
┌──────────┐    ┌──────────┐    ┌───────────┐    ┌──────────┐
│  EXPLORE │───▶│  PROPOSE │───▶│   APPLY   │───▶│  ARCHIVE │
│  想一想  │    │  写计划   │    │   写代码   │    │  存档案   │
│  不写代码 │    │  不写代码 │    │  开始干活  │    │  收尾检查  │
└──────────┘    └──────────┘    └───────────┘    └──────────┘
   可选步骤         必须步骤        必须步骤         必须步骤
```

| 命令 | 触发方式 | 做什么 | 不做什么 |
|------|---------|--------|---------|
| `/opsx:explore` | 用户输入模糊想法 | 调查代码库、比较方案、发现风险 | 不写代码、不创建文件 |
| `/opsx:propose` | 用户描述要做什么 | 创建 proposal + design + specs + tasks | 不写业务代码 |
| `/opsx:apply` | 指定变更名称 | 按 tasks 逐项写代码 | 不创建新制品 |
| `/opsx:archive` | 指定变更名称 | 检查完成情况、同步 spec、移动归档 | 不修改代码 |

## 二、提示词是怎么来的？

### 2.1 两层组装模型

每个命令给到 AI 的提示词，由**两层**组成：

```
┌─────────────────────────────────────────────────┐
│              最终提示词 = 静态 + 动态              │
│                                                 │
│  静态层（TypeScript 模板）                        │
│  ┌───────────────────────────────────────────┐  │
│  │ "你是一个提案助手，按以下步骤操作..."        │  │
│  │ 步骤1: 创建目录                              │  │
│  │ 步骤2: 获取状态                              │  │
│  │ 步骤3: 循环创建制品                          │  │
│  │ 注意事项: 不要把 context 写进文件            │  │
│  └───────────────────────────────────────────┘  │
│                      +                          │
│  动态层（CLI 运行时注入）                         │
│  ┌───────────────────────────────────────────┐  │
│  │ context: "这是一个电商平台后端"             │  │
│  │ rules: ["使用 TS 严格模式"]                 │  │
│  │ template: "## Why\n## What Changes..."     │  │
│  │ instruction: "创建提案文档，包含以下章节..." │  │
│  │ dependencies: ["proposal.md 已完成"]        │  │
│  └───────────────────────────────────────────┘  │
└─────────────────────────────────────────────────┘
```

| 层级 | 来源 | 什么时候确定 | 内容举例 |
|------|------|------------|---------|
| **静态层** | `src/core/templates/workflows/*.ts` | 代码写死 | "你该做什么、按什么步骤、注意什么" |
| **动态层** | `openspec instructions --json` CLI 输出 | 运行时生成 | "这个项目的背景、规则、模板、依赖" |

### 2.2 动态层是怎么拼出来的？

核心函数 `generateInstructions()` 的组装过程：

```
用户执行: openspec instructions proposal --change "add-jwt-auth" --json

    │
    ▼
1. 查 schema.yaml → 拿到 proposal 的 instruction（怎么写提案）
    │
    ▼
2. 读模板文件 → 拿到 proposal.md 模板（输出结构）
    │
    ▼
3. 查依赖图 → 拿到 dependencies（哪些制品已完成）
    │
    ▼
4. 查解锁列表 → 拿到 unlocks（完成后能解锁哪些制品）
    │
    ▼
5. 读项目配置 → 拿到 context + rules（项目级约束）
    │
    ▼
6. 拼成 JSON → 返回给 AI 使用
```

### 2.3 关键概念：约束与内容分离

这是最容易踩坑的设计：

```
AI 收到的 context 和 rules → 是"对 AI 的约束"，AI 要遵守，但 ❿不 ❿写进文件
AI 生成的文件内容           → 是"给用户看的内容"，才写进 .md 文件

举例：
  context = "这是一个电商平台后端"  ← AI 要知道这个背景来写提案
                                 ← 但 proposal.md 里不需要重复这句话
  rules = ["使用 TS 严格模式"]      ← AI 写代码时要遵守
                                 ← 但 tasks.md 里不需要列出这条规则
```

## 三、各阶段详细流程

### 3.1 EXPLORE 阶段 —— "先想想"

**触发命令**: `/opsx:explore [想法]`

**核心理念**: 这是一个**思考姿态**，不是工作流。没有固定步骤，不强制输出。

#### AI 的"人设"

```
你是一个"思考伙伴"，帮助用户理清思路。你的特点是：
- 好奇，不武断 → 问自然浮现的问题，不按脚本审问
- 开放，不封闭 → 抛出多个有趣方向，不急于下结论
- 可视化       → 多用 ASCII 图表帮助理解
- 适应性强     → 跟着有趣的线索走，发现新信息就调整方向
- 有耐心       → 不急于得出结论
- 接地气       → 去代码库里实地调查，不空谈
```

#### 唯一硬性约束

> **绝对不能写代码。** 如果用户让实现，提醒 ta 先退出 explore 模式。

#### 可能做的事情

```
┌─────────────────────────────────────────────┐
│              Explore 阶段                    │
│                                             │
│  🗣️ 探索问题空间                              │
│     问澄清问题、挑战假设、重新框定问题、找类比   │
│                                             │
│  🔍 调查代码库                                │
│     画架构图、找集成点、发现已有模式、揭示复杂度 │
│                                             │
│  ⚖️ 比较方案                                  │
│     头脑风暴、做对比表、画取舍分析、推荐方案     │
│                                             │
│  ⚠️ 发现风险和未知                            │
│     指出可能出错的地方、找理解盲区、建议探索方向 │
│                                             │
│  📝 捕获洞察（用户同意才做）                    │
│     新需求 → specs/<capability>/spec.md       │
│     设计决策 → design.md                      │
│     范围变化 → proposal.md                    │
│     新工作 → tasks.md                         │
└─────────────────────────────────────────────┘
```

#### 举例：用户输入 `/opsx:explore 加个暗黑模式`

```
AI: 好的，让我先看看项目的情况...

    执行: openspec list --json
    结果: 没有活跃的变更

    调查代码库:
    - 发现项目用 CSS 变量管理颜色 ✅ 好，暗黑模式容易做
    - 发现有 200+ 组件用了硬编码颜色 ⚠️ 工作量不小
    - 发现已有主题切换的 Infrastructure ❓ 需要确认

    可能的问题:
    1. 你想做简单的颜色反转，还是完整的设计系统级暗黑模式？
    2. 需要自动跟随系统设置吗？
    3. 要不要让用户手动切换？

    （这时候不写代码，只是思考和调查）
```

### 3.2 PROPOSE 阶段 —— "写计划"

**触发命令**: `/opsx:propose <描述>`

**核心产出**: 一次性创建所有制品（proposal + specs + design + tasks）

#### 完整流程图

```
用户: /opsx:propose 实现 JWT 认证系统
         │
         ▼
    ┌─────────────────────┐
    │ Step 1: 明确需求     │  ← 如果描述模糊，AI 会问"你想做什么？"
    └────────┬────────────┘
             │  确定名称: "add-jwt-auth"
             ▼
    ┌─────────────────────┐
    │ Step 2: 创建目录     │  ← openspec new change "add-jwt-auth"
    │                      │    创建: openspec/changes/add-jwt-auth/
    └────────┬────────────┘
             │
             ▼
    ┌─────────────────────┐
    │ Step 3: 获取构建顺序 │  ← openspec status --json
    │                      │    拿到: applyRequires=["tasks"]
    │                      │    拿到: 4个制品的状态和依赖关系
    └────────┬────────────┘
             │
             ▼
    ┌─────────────────────┐
    │ Step 4: 循环创建制品 │  ← 按依赖顺序，一个接一个
    │                      │
    │   4a. proposal      │  ← 无依赖，第一个创建
    │       读取: 无       │
    │       输出: proposal.md
    │         │
    │         ▼
    │   4b. specs         │  ← 依赖 proposal
    │   4c. design        │  ← 依赖 proposal（和 specs 并行）
    │       读取: proposal.md
    │       输出: specs/auth/spec.md + design.md
    │         │
    │         ▼
    │   4d. tasks         │  ← 依赖 specs + design
    │       读取: specs/auth/spec.md + design.md
    │       输出: tasks.md
    └────────┬────────────┘
             │
             ▼
    ┌─────────────────────┐
    │ Step 5: 显示最终状态 │  ← openspec status
    └─────────────────────┘
```

#### 每个制品的指令结构

以 **proposal** 为例，AI 执行 `openspec instructions proposal --json` 后收到：

```json
{
  "artifactId": "proposal",
  "outputPath": "proposal.md",

  "instruction": "创建提案文档，包含 Why、What Changes、Capabilities、Impact 章节...",
  "template": "## Why\n<!-- 说明动机 -->\n\n## What Changes\n<!-- 说明变更 -->\n...",
  "context": "这是一个电商平台后端，使用 Node.js + TypeScript",
  "rules": ["使用 TypeScript 严格模式", "API 必须返回标准错误格式"],

  "dependencies": [],
  "unlocks": ["specs", "design"]
}
```

| 字段 | 作用 | AI 怎么用 |
|------|------|----------|
| `instruction` | 怎么写这个制品的指导 | 按指导写内容 |
| `template` | 文件结构模板 | 按这个骨架填内容 |
| `context` | 项目背景（⚠️ 不写入文件） | 理解上下文来写 |
| `rules` | 项目规则（⚠️ 不写入文件） | 遵守规则来写 |
| `dependencies` | 依赖的已完成制品 | 先读这些文件了解上下文 |
| `unlocks` | 完成后解锁的制品 | 告诉 AI 接下来能做什么 |

#### specs 制品举例

specs 的 instruction 更具体，因为它要求严格的格式：

```json
{
  "artifactId": "specs",
  "instruction": "创建规格文件，定义系统应该做什么。\n\n增量操作（用 ## 标题）:\n- ADDED: 新增需求\n- MODIFIED: 修改需求\n- REMOVED: 废弃功能\n- RENAMED: 仅改名\n\n格式要求:\n- 每个需求: ### Requirement: <名称>\n- 使用 SHALL/MUST 表达规范性要求\n- 每个场景: #### Scenario: <名称>，用 WHEN/THEN 格式\n- 每个需求必须至少有一个场景",
  "dependencies": [
    {
      "id": "proposal",
      "done": true,
      "path": "proposal.md"
    }
  ]
}
```

#### tasks 制品举例

tasks 要求严格的 checkbox 格式，因为 apply 阶段要解析它：

```json
{
  "artifactId": "tasks",
  "instruction": "创建任务列表，拆分实现工作。\n\n重要：必须严格使用 checkbox 格式 `- [ ]`，否则 apply 阶段无法追踪进度。\n\n指南:\n- 用 ## 编号标题分组\n- 每个任务必须是 checkbox: `- [ ] X.Y 任务描述`\n- 任务要足够小，一次会话能完成\n- 按依赖关系排序",
  "template": "## 1. 任务组名\n- [ ] 1.1 任务描述\n- [ ] 1.2 任务描述",
  "dependencies": [
    {"id": "specs", "done": true, "path": "specs/auth/spec.md"},
    {"id": "design", "done": true, "path": "design.md"}
  ]
}
```

#### 最终产出物

```
openspec/changes/add-jwt-auth/
├── .openspec.yaml          ← 变更配置（自动创建）
├── proposal.md             ← 为什么做、做什么、影响范围
├── design.md               ← 怎么做、技术决策、风险
├── tasks.md                ← 实施清单（checkbox 格式）
└── specs/
    └── auth/
        └── spec.md         ← 需求规格（WHEN/THEN 场景）
```

### 3.3 APPLY 阶段 —— "开始干活"

**触发命令**: `/opsx:apply [变更名称]`

**核心逻辑**: 读所有上下文文件 → 按 tasks.md 逐项实现 → 打勾标记完成

#### 完整流程图

```
用户: /opsx:apply add-jwt-auth
         │
         ▼
    ┌──────────────────────┐
    │ Step 1: 确定变更     │  ← 有参数直接用；没有就推断或让用户选
    └────────┬─────────────┘
             │
             ▼
    ┌──────────────────────┐
    │ Step 2: 检查状态     │  ← openspec status --json
    │                      │    确认 schema、制品是否就绪
    └────────┬─────────────┘
             │
             ▼
    ┌──────────────────────┐
    │ Step 3: 获取实施指令 │  ← openspec instructions apply --json
    │                      │    拿到: 上下文文件列表 + 任务列表 + 进度
    └────────┬─────────────┘
             │
             ▼
    ┌──────────────────────┐
    │ Step 4: 读上下文文件 │  ← 读 proposal + specs + design + tasks
    └────────┬─────────────┘
             │
             ▼
    ┌──────────────────────┐
    │ Step 5: 显示进度     │  ← "2/7 已完成，还有 5 个任务"
    └────────┬─────────────┘
             │
             ▼
    ┌──────────────────────┐
    │ Step 6: 循环实现任务 │  ← 逐个完成 pending 任务
    │                      │
    │   任务 2.1           │  ← 实现 token 生成接口
    │   任务 2.2           │  ← 实现 token 验证中间件
    │   任务 2.3           │  ← 实现 token 刷新接口
    │   任务 3.1           │  ← 写单元测试
    │   任务 3.2           │  ← 写集成测试
    │                      │
    │   每完成一个:        │  ← `- [ ]` → `- [x]`
    │   遇到阻塞就暂停:     │  ← 任务不清/设计问题/报错
    └────────┬─────────────┘
             │
             ▼
    ┌──────────────────────┐
    │ Step 7: 显示最终状态 │  ← 全部完成 或 暂停原因
    └──────────────────────┘
```

#### Apply 指令 JSON 示例

```json
{
  "changeName": "add-jwt-auth",
  "schemaName": "spec-driven",
  "contextFiles": {
    "proposal": [".../proposal.md"],
    "specs": [".../specs/auth/spec.md"],
    "design": [".../design.md"],
    "tasks": [".../tasks.md"]
  },
  "progress": { "total": 7, "complete": 2, "remaining": 5 },
  "tasks": [
    {"id": "1", "description": "1.1 创建 JWT 工具模块", "done": true},
    {"id": "2", "description": "1.2 添加 JWT 依赖", "done": true},
    {"id": "3", "description": "2.1 实现 token 生成接口", "done": false},
    {"id": "4", "description": "2.2 实现 token 验证中间件", "done": false},
    {"id": "5", "description": "2.3 实现 token 刷新接口", "done": false},
    {"id": "6", "description": "3.1 写 JWT 模块单元测试", "done": false},
    {"id": "7", "description": "3.2 写认证流程集成测试", "done": false}
  ],
  "state": "in_progress",
  "instruction": "读上下文文件，逐个完成任务，完成后打勾。遇到阻塞就暂停。"
}
```

#### 三种状态处理

```
┌─────────────────────────────────────────────────────────┐
│                   Apply 的三种状态                       │
│                                                         │
│  ✅ in_progress（进行中）                                  │
│     → 正常循环实现任务                                     │
│                                                         │
│  🚧 blocked（被阻塞）                                     │
│     → 缺少制品（如 design、tasks 未完成）                   │
│     → 提示用户: "先用 /opsx:continue 创建缺失的制品"       │
│                                                         │
│  🎉 all_done（全部完成）                                  │
│     → 恭喜用户                                            │
│     → 建议: "可以用 /opsx:archive 归档了"                 │
└─────────────────────────────────────────────────────────┘
```

#### 暂停条件

AI 在以下情况会**暂停实现**，等待用户指示：

| 情况         | AI 行为     |
| ---------- | --------- |
| 任务描述不清楚    | 问用户澄清     |
| 实现时发现设计问题  | 建议更新制品文件  |
| 遇到编译/运行时错误 | 报告错误，等待指导 |

### 3.4 ARCHIVE 阶段 —— "存档案"

**触发命令**: `/opsx:archive [变更名称]`

**核心逻辑**: 检查完整性 → 同步 spec → 移动到归档目录

#### 完整流程图

```
用户: /opsx:archive add-jwt-auth
         │
         ▼
    ┌─────────────────────┐
    │ Step 1: 确认变更     │  ← 必须用户亲自选，AI 不自动选
    └────────┬────────────┘
             │
             ▼
    ┌─────────────────────┐
    │ Step 2: 检查制品     │  ← 所有制品都完成了吗？
    │                      │    没有 → 警告 + 确认是否继续
    └────────┬────────────┘
             │
             ▼
    ┌─────────────────────┐
    │ Step 3: 检查任务     │  ← tasks.md 里都打勾了吗？
    │                      │    没打完 → 警告 + 确认是否继续
    └────────┬────────────┘
             │
             ▼
    ┌─────────────────────┐
    │ Step 4: 评估 Spec   │  ← 有 delta spec 文件吗？
    │        同步状态      │    有 → 对比主 spec，展示差异
    │                      │    问用户: "现在同步？还是直接归档？"
    └────────┬────────────┘
             │  用户选择同步
             ▼
    ┌─────────────────────┐
    │ Step 4b: 同步 Spec  │  ← 把变更的 spec 合并到主 spec
    │         (可选)       │    ADDED → 添加到主 spec
    │                      │    MODIFIED → 更新主 spec
    │                      │    REMOVED → 从主 spec 删除
    │                      │    RENAMED → 在主 spec 改名
    └────────┬────────────┘
             │
             ▼
    ┌─────────────────────┐
    │ Step 5: 执行归档     │  ← mkdir -p archive
    │                      │    mv changes/add-jwt-auth
    │                      │       → archive/2026-06-18-add-jwt-auth/
    └────────┬────────────┘
             │
             ▼
    ┌─────────────────────┐
    │ Step 6: 显示摘要     │  ← 变更名、Schema、归档路径、Spec 状态
    └─────────────────────┘
```

#### 成功输出示例

```
## Archive Complete

Change:  add-jwt-auth
Schema:  spec-driven
Archived to: openspec/changes/archive/2026-06-18-add-jwt-auth/
Specs:   ✓ Synced to main specs

All artifacts complete. All tasks complete.
```

## 四、其他辅助命令

### 4.1 `/opsx:new` —— "先建个空目录"

和 `propose` 的区别：**只创建目录，不生成制品**。停在第 6 步等用户指示。

```
适用场景: 用户想一步一步来，不想让 AI 一口气生成所有制品

流程:
1. 确定变更名称
2. 选择 workflow schema（默认 spec-driven）
3. 创建目录: openspec/changes/<name>/
4. 显示制品状态
5. 获取第一个制品的指令
6. 停下来，等用户指示 ← 关键区别！
```

### 4.2 `/opsx:continue` —— "继续写下一个制品"

适用于用 `/opsx:new` 创建了空变更后，逐步创建制品。

```
流程:
1. 确定变更
2. 查状态 → 找到下一个 "ready" 的制品
3. 获取指令 → 读依赖文件 → 创建制品
4. 显示简要进度
5. 完成一个就停（用户可以继续调用 continue 创建下一个）
```

### 4.3 `/opsx:ff` (Fast-Forward) —— "快速补齐所有制品"

```
适用场景: 变更目录已存在，但制品还没写全，想一口气补齐

和 propose 的区别:
- propose: 先创建变更目录 → 再生成制品
- ff:      假设目录已存在 → 只生成缺失的制品
```

### 4.4 `/opsx:verify` —— "验证实现是否符合计划"

```
三个验证维度:
1. 完整性: 所有任务都实现了吗？
2. 正确性: 实现符合 spec 吗？
3. 一致性: 代码遵循 design 决策吗？
```

### 4.5 `/opsx:sync` —— "同步 Delta Spec 到主 Spec"

```
适用场景: 归档前想手动同步 spec

操作:
1. 读变更的 delta spec: openspec/changes/<name>/specs/
2. 读主 spec: openspec/specs/
3. 应用增量操作: ADDED / MODIFIED / REMOVED / RENAMED
4. 显示变更摘要
```

## 六、关键设计模式总结

### 6.1 约束与内容分离（最重要！）

```
┌─────────────────────────────────────────────────┐
│            这是最容易被误解的设计                 │
│                                                 │
│  AI 收到的信息分为两类:                           │
│                                                 │
│  📌 约束信息（context + rules）                   │
│     → AI 要遵守                                   │
│     → ❿不❿写入文件                               │
│     → 例如: "这是电商后端"、"用 TS 严格模式"      │
│                                                 │
│  📄 内容信息（template + instruction）            │
│     → AI 按此生成文件内容                          │
│     → 写入 .md 文件                              │
│     → 例如: proposal.md 的章节结构                │
└─────────────────────────────────────────────────┘
```

### 6.2 Schema 驱动

```
schema.yaml 是整个工作流的"操作系统"：

artifacts:
  - id: proposal
    instruction: "创建提案文档..."     ← 告诉 AI 怎么写
    generates: "proposal.md"           ← 输出文件名
    requires: []                       ← 无依赖

  - id: specs
    instruction: "创建规格文件..."
    generates: "specs/**/*.md"
    requires: [proposal]               ← 依赖 proposal

apply:
  requires: [tasks]                    ← 实施前必须完成 tasks
  tracks: tasks.md                     ← 用 tasks.md 追踪进度
  instruction: "读上下文，逐个完成任务"  ← 实施指导
```

### 6.3 依赖驱动执行

```
proposal (无依赖)
    │
    ├──→ specs (依赖 proposal) ──┐
    │                            ├──→ tasks (依赖 specs + design)
    └──→ design (依赖 proposal) ─┘

AI 的行为:
1. 查 status → 知道哪些制品 "ready"（依赖已满足）
2. 只创建 ready 的制品
3. 创建完成后，依赖它的制品变为 "ready"
4. 循环，直到所有 applyRequires 完成
```

### 6.4 项目配置注入

```
项目根目录的 openspec/config.yaml:

context: |
  这是一个电商平台后端，使用 Node.js + TypeScript。
  使用 RESTful API 风格。

rules:
  proposal:
    - 提案必须包含影响分析
  tasks:
    - 每个任务必须可独立测试
    - 必须包含测试任务

→ 这些会被注入到每个制品的 context 和 rules 字段
→ 影响所有制品的生成方式
```
