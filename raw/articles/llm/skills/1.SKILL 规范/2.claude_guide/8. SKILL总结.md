# 8. SKILL 总结

> 用大白话讲清楚：什么是 Skill，怎么建、怎么组合、怎么调。

---

## 一、什么是 Skill？一句话说明白

**Skill 就是一个"专业技能包"**。

你可以把它理解成：给 Claude 装上一个"插件"，让它在某个特定领域变成专家。

举个生活中的例子：

> Claude 本身是一个啥都会一点的"全科医生"。
> 你给它装上"Excel Skill"，它就变成了"财务分析师"。
> 你给它装上"代码审查 Skill"，它就变成了"资深工程师"。

**官方定义**：Skill 是一个文件夹，里面装着指令、脚本和参考资料，Claude 会在需要的时候自动加载。

---

## 二、为什么要用 Skill？（解决什么痛点）

| 痛点 | 没有 Skill 时 | 有了 Skill 后 |
|------|--------------|--------------|
| 每次都要写长 Prompt | 反复复制粘贴同样的提示词 | 一次写好，反复使用 |
| Claude 偶尔出错 | 每次结果不稳定 | 流程固化，结果一致 |
| 团队标准不统一 | 每个人让 Claude 输出的格式不一样 | 全公司统一标准 |
| 上下文窗口不够用 | 把所有知识一次性塞给 Claude | 按需加载，用到的才加载 |
| 精确任务做不好 | 让 Claude 算数学，偶尔算错 | 交给脚本，100% 准确 |

**关键洞察**：
- 小模型 + 好 Skill，效果可以逼近大模型裸跑 → 省钱
- 高质量 Skill 是工程化的产物，不是随便写写就行

---

## 三、Skill 的核心结构（三层模型）

理解 Skill，最关键的是理解**三层架构**。打个比方：

```
Skill = 一本书

L1 封面（Metadata）    → 书名 + 简介，随时都能看到，决定是否翻开这本书
L2 正文（Instructions） → 只有翻开才看到具体操作指南
L3 附录（Resources）    → 脚本、参考文档、模板，需要时才查阅
```

| 层级         | 放什么                          | 什么时候加载    | 设计原则                  |
| ---------- | ---------------------------- | --------- | --------------------- |
| **L1 元数据** | `name` 和 `description`       | 永远加载（启动时） | 要"轻"：只写做什么、何时做，不写具体步骤 |
| **L2 指令**  | `SKILL.md` 正文                | 被触发时才加载   | 要"准"：聚焦执行逻辑、步骤、边界     |
| **L3 资源**  | scripts/、references/、assets/ | 需要时才读取    | 要"全"：把复杂逻辑和知识库沉到这里    |

**黄金原则**：
- L1 写不好 → Skill 不会被触发（Claude 不知道什么时候该用它）
- L2 写不好 → Skill 触发后执行错乱（Claude 不知道怎么干）
- L3 写不好 → 上下文爆炸（把一堆无关信息塞进去了）

## 四、Skill 的文件夹结构

一个 Skill 就是一个文件夹，结构如下：

```
my-skill/
├── SKILL.md             ← 核心文件！必须有，定义元数据 + 指令
├── scripts/             ← 可选：Python/Bash 脚本（处理精确任务）
│   └── process.py
├── references/          ← 可选：参考文档（大段知识放这里）
│   └── style-guide.md
├── assets/              ← 可选：模板、示例文件
│   └── template.docx
└── examples/            ← 可选：输入输出示例（Few-Shot）
    ├── input_1.txt
    └── output_1.txt
```

**最简形态**：只有一个 `SKILL.md` 文件就足够了，其他目录按需添加。

## 五、SKILL.md 怎么写？（核心文件）

### 5.1 文件格式

```yaml
---
name: my-skill-name          # 唯一标识，小写字母+连字符，最多64字符
description: "这里写触发描述"  # 最关键字段！决定 Claude 何时调用
---

# 以下正文只在 Skill 被触发后才加载

## Overview
功能概述...

## Instructions
具体执行步骤...
```

### 5.2 description 怎么写？（最重要的字段）

这是整个 Skill 的"路由规则"，写不好 Skill 就不会被触发。

**错误写法（太模糊）**：
```
This skill helps with PDFs and documents.
```
问题：Claude 不知道具体能做什么、什么时候该用。

**正确写法（具体明确）**：
```
Comprehensive PDF manipulation toolkit for extracting text and tables,
creating new PDFs, merging/splitting documents, and handling forms.
When Claude needs to fill in a PDF form or programmatically process,
generate, or analyze PDF documents at scale.
Not for simple PDF viewing or basic conversions.
```

这个好版本包含了三件事：
1. **具体能力**：能提取、能创建、能合并分割、能处理表单
2. **触发场景**：填表单、批量处理
3. **排除边界**：不用于简单的查看或基础转换

**一句话口诀**：description 不是广告文案，是路由标签。写得越像"精确的任务分流标签"，触发质量越高。

### 5.3 description 强弱对照表

| 弱 description       | 强 description                                                                                                          |
| ------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| "Helps with PDFs"   | "Extract tables from PDFs, merge/split documents, fill forms. Use for batch processing. Not for simple viewing."       |
| "Code review skill" | "Reviews code for OWASP Top 10 vulnerabilities, enforces company style guide, outputs severity-ranked findings table." |
| "Writing helper"    | "Transforms rough notes into polished blog posts following SEO best practices. Outputs markdown with frontmatter."     |

### 5.4 完整字段表（Claude Code 扩展字段）

| 字段                         | 用途              | 举例                                        |
| -------------------------- | --------------- | ----------------------------------------- |
| `name`                     | Skill 名字，默认取目录名 | `pdf-editor`                              |
| `description`              | 何时使用            | "处理 PDF 文件时..."                           |
| `when_to_use`              | 补充触发场景          | "例如：提取表格、合并文档"                            |
| `argument-hint`            | 参数提示            | `[file-path]`                             |
| `disable-model-invocation` | 禁止 Claude 自动调用  | `true` → 只能手动 `/skill` 触发                 |
| `user-invocable`           | 是否对用户可见         | `false` → 只自动触发，菜单里不显示                    |
| `allowed-tools`            | 激活时免确认的工具       | `Read Grep Bash(git add *)`               |
| `disallowed-tools`         | 激活时禁用的工具        | `AskUserQuestion`                         |
| `model`                    | 指定使用的模型         | `sonnet` / `opus` / `haiku`               |
| `effort`                   | 推理强度            | `low` / `medium` / `high` / `xhigh`       |
| `context: fork`            | 在子代理中执行         | 让 Skill 在独立环境中跑                           |
| `agent`                    | 子代理类型           | `Explore`（只读）/ `Plan` / `general-purpose` |
| `paths`                    | 限制激活的文件范围       | `*.go,internal/**/*.go`                   |
| `shell`                    | 脚本解释器           | `bash`（默认）/ `powershell`                  |

### 5.5 完整实战样例：一个 PDF 处理 Skill

下面是一个结构完整、可直接使用的 Skill，涵盖了前面讲到的所有要点：

```
pdf-toolkit/
├── SKILL.md              ← 核心文件（见下方完整代码）
├── scripts/
│   └── extract_text.py   ← 低自由度任务：精确提取文本
├── references/
│   └── api-reference.md  ← 大段知识下沉，按需加载
└── examples/
    ├── simple.pdf
    └── form-sample.pdf
```

```yaml
---
name: pdf-toolkit
description: |
  Comprehensive PDF manipulation: extract text/tables, merge/split pages,
  fill form fields, and analyze document structure. Use when Claude needs
  to (1) pull data out of PDFs, (2) combine or divide PDF files,
  (3) programmatically fill or edit PDF forms. Not for simple PDF viewing
  or image-only PDFs.
when_to_use: |
  例如：提取合同条款、合并多个报告、填写申报表、分析发票数据
allowed-tools: Read Bash(python *) Bash(ls *) Bash(cat *)
paths: *.pdf
---

# PDF Toolkit

## Workflow Decision Tree

根据任务类型选择对应流程：

### 提取文本/表格
1. 运行 `python scripts/extract_text.py <file>` 获取纯文本
2. 如需保留表格结构，读取 `references/api-reference.md` 中的 table 提取方法
3. 输出结构化结果

### 合并/分割 PDF
1. 确认输入文件列表或页码范围
2. 使用 PyPDF2/pymupdf 脚本操作（见 `references/api-reference.md`）
3. 输出合并后的文件路径

### 填写 PDF 表单
1. 先运行 `python scripts/extract_text.py <file> --fields` 提取表单字段名
2. 让用户确认字段值映射
3. 填充并输出新文件

## Constraints
- 所有脚本必须使用相对路径引用（相对于 Skill 根目录）
- 遇到加密 PDF 时，明确告知用户无法处理，不要静默失败
- 图片型 PDF（扫描件）无法直接提取文字，需提示用户先做 OCR
- 输出文件统一放在同目录的 `output/` 文件夹下

## Error Handling
脚本失败时必须在 stderr 打印清晰错误信息，例如：
- `[ERROR] File not found: xxx.pdf`
- `[ERROR] Unsupported PDF encryption`
- `[ERROR] No form fields detected`

这样 Claude 才能读懂错误原因并尝试自我修复。

## Quick Reference
- 详细 API 用法、边界情况处理 → `references/api-reference.md`
- 示例文件 → `examples/` 目录
```

**这个样例的关键设计点**：

| 设计 | 体现 |
|------|------|
| **description 精准** | 用动词列举能力（extract, merge, fill），包含 Not for 排除边界 |
| **when_to_use 补充** | 用中文给出具体场景示例，降低触发门槛 |
| **paths 限定范围** | 只在操作 `*.pdf` 文件时自动激活，避免误触发 |
| **allowed-tools 提速** | 预授权只读工具，减少用户确认步骤 |
| **决策树结构** | 三种场景（提取/合并/填表）各走不同流程 |
| **脚本处理精确任务** | 文本提取用 Python 脚本，不靠 Prompt 模拟 |
| **知识下沉** | 详细 API 放到 references/，主文件保持精简 |
| **错误提示清晰** | 约定 stderr 输出格式，让 Claude 能读懂并自我修复 |

## 六、如何创建 Skill？（六步工作流）

### Step 1: Understand（理解）

先搞清楚：
- 这个 Skill 要解决什么痛点？
- 最好的结果长什么样？
- 最坏的情况可能出什么问题？

### Step 2: Plan（规划）

设计文件结构：
- 哪些放 `SKILL.md`（Prompt/指令）？
- 哪些写成 Python 脚本（精确计算、格式转换）？
- 哪些放 references/（大段知识）？

**设计原则**：
- 确定性任务（Low DoF）→ 用脚本
- 创造性任务（High DoF）→ 用 Prompt

### Step 3: Init（初始化）

用脚手架生成标准结构，不要从零手写 YAML。

```bash
python scripts/init_skill.py my-new-skill
```

### Step 4: Edit（编写）

**顺序很重要**：
1. 先写资源：scripts/*.py、references/、assets/
2. 再写指令：SKILL.md（胶水层）

为什么先写资源？因为 Prompt 要指向真实存在的文件。

### Step 5: Validate（验证）

- 检查 YAML 语法是否正确
- 检查文件引用路径是否正确
- 模拟基本调用是否成功

### Step 6: Iterate（迭代）

根据实际使用反馈，不断微调 description 和 instructions。

## 八、核心设计原则：自由度（DoF）

这是写 Skill 最重要的判断标准：

| 任务属性 | 高自由度（High DoF） | 低自由度（Low DoF） |
|---------|---------------------|-------------------|
| 特点 | 需要创意、灵活、多种结果都可 | 需要精确、零容错、格式固定 |
| 例子 | 写诗、设计网页、总结文章 | 数学计算、JSON 生成、文件转换 |
| 实现方式 | **写 Markdown 指令**（Prompt） | **写 Python 脚本**（Script） |
| 原因 | 给 Claude 发挥空间 | Claude 不适合模拟计算机，交给代码 |

**黄金法则**：
> 如果任务逻辑是"脆弱的"（改一个字就报错），请写代码；
> 如果任务需要"弹性"（多种结果都可接受），请写 Prompt。

## 九、Skill 组合（多 Skill 协同）

单个 Skill 只能干一件事，复杂任务需要多个 Skill 配合。

### 9.1 串行链式（Chaining）

一个 Skill 的输出 → 下一个 Skill 的输入

```
Research Skill → Copywriting Skill → Compliance Skill → 最终文章
```

举例：写一篇文章
1. Research Skill 联网搜索，输出研究简报
2. Copywriting Skill 把简报写成公众号文章
3. Compliance Skill 检查是否违反广告法，输出合规文章

### 9.2 动态路由（Dynamic Routing）

智能分发，根据用户意图自动选择最合适的 Skill

```
用户提问
    ├── 涉及数据库 → SQL Skill
    ├── 涉及画图 → Chart Skill
    └── 复杂逻辑 → Python Skill
```

### 9.3 冲突解决

当两个 Skill 指令冲突时（比如一个说"尽量发挥创意"，一个说"严谨不要过度承诺"）：

**解决方案**：流水线编排
```
Creative Skill（生成内容）→ Legal Skill（审核把关）→ 最终输出
```

让"守门员"Skill 放在流水线末端。

### 9.4 团队共享

像管理代码库一样管理 Skills：

```
internal-skills/（内部 git 仓库）
├── marketing/social-media-expert/
├── engineering/python-guru/
└── hr/policy-qa/
```

加上版本控制，防止 Skill 升级导致原有业务崩溃。

## 十、如何调试和优化 Skill？

### 10.1 常见问题排查

| 问题 | 症状 | 排查方法 |
|------|------|---------|
| **Skill 没被触发** | Claude 说"我不知道怎么做" | 1. 文件名必须是 `SKILL.md`（全大写）<br>2. 路径是否正确<br>3. YAML 格式是否有误<br>4. description 是否够具体 |
| **触发错了 Skill** | 要 A 功能，调用了 B Skill | 1. 检查 description 是否有重叠<br>2. 加"Not for..."排除边界<br>3. 用差异化关键词 |
| **参数传递错误** | 脚本报错缺少参数 | 1. SKILL.md 中增加示例说明如何提取参数<br>2. 脚本处理默认值和边界情况 |
| **脚本执行失败** | Skill 调了但脚本报错 | 1. 本地独立测试脚本<br>2. 检查依赖是否安装<br>3. 检查文件路径用相对路径<br>4. 确保错误信息打印到 stderr |

### 10.2 性能优化

| 优化方向 | 做法 |
|---------|------|
| **减少上下文消耗** | 不要把整个 API 文档塞进去，只放真正需要的部分；用渐进式披露（拆分子文件） |
| **脚本优先于 Prompt** | 精确任务用脚本：速度更快、100% 准确、Token 消耗更低 |
| **预授权只读工具** | 在 frontmatter 声明 `allowed-tools: Read Grep`，减少用户确认步骤 |

### 10.3 A/B 对比测试

怀疑 Skill 效果不好时：
1. 禁用 Skill，用纯 Prompt 完成同一任务
2. 启用 Skill，完成同一任务
3. 对比：准确性、速度、Token 消耗

### 10.4 最佳实践清单

- [ ] **单一职责**：一个 Skill 只干一件事，别做万能 Skill
- [ ] **description 具体**：写清楚适用场景 + 不适用场景
- [ ] **脚本独立**：底层脚本能本地独立运行，方便测试
- [ ] **错误提示清晰**：失败时打印具体原因，别只返回 Exit Code 1
- [ ] **版本号标注**：便于团队协作追踪变更
- [ ] **持续迭代**：根据反馈微调 description 和 instructions

## 十一、Skill vs 其他概念的对比

| 概念 | 本质 | 类比 | 何时用 |
|------|------|------|--------|
| **System Prompt** | 对话开场白 | 设定角色人设 | 单次会话，设定整体风格 |
| **Projects** | 知识库容器 | 图书馆 | 存放参考文档供检索（静态知识：What to know） |
| **MCP** | 外部连接协议 | 电话线 | 连接 Notion、Slack 等外部数据（外部数据：Where to look） |
| **Skills** | 专业能力包 | 工具箱 | 封装特定任务的最佳实践和执行方法（How to do） |

**一个实际例子**：
- Project：存放公司的品牌规范 PDF（静态知识）
- MCP：连接 Figma 获取设计稿（外部数据）
- Skill：封装如何根据品牌规范检查设计稿的具体流程（执行方法）

## 十四、关键概念速查

| 概念                  | 大白话解释                                             |
| ------------------- | ------------------------------------------------- |
| **渐进式披露**           | 不要一次性把所有知识塞给 Claude，用到的时候再加载                      |
| **自由度（DoF）**        | 任务有多灵活：高自由度用 Prompt，低自由度用脚本                       |
| **Description**     | Skill 的路由标签，决定 Claude 什么时候调用它                     |
| **SKILL.md**        | Skill 的核心文件，YAML 头部 + Markdown 正文                 |
| **L1/L2/L3**        | 信息三层：元数据（永远在）→ 指令（触发才加载）→ 资源（按需读取）                |
| **Skill Chaining**  | 多个 Skill 串行配合，前一个的输出是后一个的输入                       |
| **Dynamic Routing** | 智能分发，根据意图自动选择最合适的 Skill                           |
| **Fork 模式**         | Skill 在子代理中执行，独立环境不影响主对话                          |
| **内联 Shell 注入**     | `` !`command` `` 语法，在 Skill 内容送达 Claude 之前先执行命令替换 |

## 十五、一句话总结

> **Skill 就是把"怎么做某件事"的专业知识打包成一个文件夹，让 Claude 在需要的时候自动变成专家。**
>
> 写好 Skill 的关键：description 写准路由，正文写清流程，脚本处理精确任务，知识按需加载。
